# اتصال به سامانه تیکتینگ موجود (PHP)

هدف: سامانه اتوماسیون اداری (این پروژه) و سامانه تیکتینگ PHP موجود، به یک سامانه واحد برای کاربر تبدیل شوند —
یک ورود، یک فهرست کاربران، و تبادل اطلاعات تیکت/درخواست بدون کار دستی.

## ۱. وضعیت فعلی و آنچه ساخته شده

در این پروژه زیرساخت اتصال آماده است:

| قابلیت | مسیر / کلاس |
| --- | --- |
| صدور نشانه دسترسی | `POST /api/v1/auth/token` |
| اطلاعات کاربر جاری | `GET /api/v1/auth/me` |
| ساختار سازمانی | `GET /api/v1/departments`, `GET /api/v1/departments/tree` |
| مدیریت واحدها | `POST/PUT/DELETE /api/v1/departments` |
| بررسی سلامت سرویس | `GET /api/v1/health` |
| سیاست دسترسی برنامه‌نویسی | `AppPolicies.ApiAccess` |

**نمونه دریافت نشانه و فراخوانی سرویس (از سمت PHP):**

```bash
# ۱) دریافت نشانه
curl -X POST http://automation.local/api/v1/auth/token \
  -H "Content-Type: application/json" \
  -d '{"userName":"admin","password":"********"}'

# ۲) فراخوانی سرویس با نشانه
curl http://automation.local/api/v1/departments/tree \
  -H "Authorization: Bearer <ACCESS_TOKEN>"
```

## ۲. سه سناریوی اتصال (یکی را انتخاب کنید)

### سناریو الف — احراز هویت واحد (SSO) با JWT  ⭐ پیشنهاد ما
1. کاربر در سامانه اتوماسیون وارد می‌شود.
2. سامانه اتوماسیون برای او نشانه کوتاه‌عمر (مثلاً ۵ دقیقه) با ادعای «هدف: ticketing» صادر می‌کند.
3. کاربر با نشانی `https://ticketing.local/sso?token=...` به سامانه تیکتینگ هدایت می‌شود.
4. سامانه PHP نشانه را با **کلید مشترک** اعتبارسنجی می‌کند و نشست کاربر را می‌سازد.
5. اگر کاربر در سامانه تیکتینگ وجود نداشت، به‌صورت خودکار ساخته می‌شود (Just-In-Time Provisioning).

**مزایا:** یک ورود، بدون همگام‌سازی مداوم کاربران، بدون ذخیره گذرواژه در دو جا.
**کار لازم در سمت PHP:** یک اکشن SSO (حدود ۵۰ خط) + اعتبارسنجی امضای JWT (کتابخانه `firebase/php-jwt`).

### سناریو ب — همگام‌سازی دوره‌ای (Sync)
سامانه اتوماسیون هر ساعت/روز، فهرست کاربران و واحدها را با فراخوانی API به سامانه تیکتینگ می‌فرستد (یا برعکس).
مناسب زمانی که تغییر در سامانه PHP سخت است.

**مزایا:** نیازی به تغییر ساختار ورود سامانه PHP نیست.
**معایب:** داده‌ها ممکن است چند ساعت عقب باشند؛ کاربر دو حساب دارد.

### سناریو ج — نگاشت پایگاه‌داده (Database Bridge)
یک جدول/ویو نگاشت (مثلاً `bridge_employees`) در پایگاه‌داده مشترک یا از طریق Stored Procedure.
**فقط به‌عنوان راه‌حل موقت** توصیه می‌شود؛ وابستگی سخت به جزئیات پیاده‌سازی دو سامانه می‌سازد.

## ۳. چه داده‌ای باید نگاشت شود؟

| سامانه اتوماسیون | سامانه تیکتینگ (PHP) | نکته |
| --- | --- | --- |
| `Users.Id` (Guid) | `users.id` (int) | جدول نگاشت `IntegrationUserMap(AutomationUserId, TicketingUserId)` لازم است |
| `Departments` | `departments` / `units` | نگاشت بر پایه «کد واحد» یا نام یکسان |
| `Employees` | `users` (فیلد پرسنلی) | کلید مشترک پیشنهادی: کد ملی یا کد پرسنلی |
| نقش‌ها | نقش‌ها/سطوح دسترسی | نگاشت نقش به نقش (مدیر سیستم ↔ admin) |
| تیکت/درخواست | `tickets` | اینکه تیکت‌ها در کدام سامانه «مالک» دارند، باید یک‌بار و برای همیشه تصمیم‌گیری شود |

**قاعده طلایی:** برای هر نوع داده، **یک سامانه مالک (Single Source of Truth)** تعیین کنید. پیشنهاد:
- کاربران و ساختار سازمانی → سامانه اتوماسیون مالک است
- تیکت‌ها و گفت‌وگوی پشتیبانی → سامانه تیکتینگ مالک است

## ۴. گام‌های اجرایی پیشنهادی

1. **تعیین مالکیت داده** (جدول بالا) — یک جلسه با تیم تیکتینگ.
2. **تثبیت قرارداد API**: نسخه، مسیر، ساختار خطا، محدودیت نرخ (Rate Limit).
3. **افزودن جدول نگاشت** `IntegrationUserMap` در این پروژه.
4. **پیاده‌سازی SSO در سمت PHP** (سناریو الف) با کلید مشترک و انقضای کوتاه.
5. **آزمون روی محیط آزمایشی** (نه عملیاتی) با کاربر نمونه.
6. **ثبت رویدادهای اتصال** در گزارش ممیزی (موفق/ناموفق) برای پیگیری.
7. **راه‌اندازی اعلان یکپارچه**: رویداد تیکت جدید → اعلان در سامانه اتوماسیون (و برعکس).

## ۵. ملاحظات امنیتی

- نشانه دسترسی را **هرگز** در URL طولانی‌عمر یا کوکی ناامن قرار ندهید.
- کلید امضا را از متغیر محیطی بخوانید (`Jwt__SigningKey`)، نه از کد.
- تبادل را روی **HTTPS** انجام دهید؛ اگر سامانه PHP فقط HTTP دارد، ابتدا آن را اصلاح کنید.
- محدودیت نرخ روی مسیر `POST /api/v1/auth/token` بگذارید (جلوگیری از حمله فرهنگ‌نامه‌ای).
- نشانه SSO باید یک‌بارمصرف و کوتاه‌عمر باشد و ادعای `aud`/`iss` بررسی شود.
- تمام فراخوانی‌ها را در گزارش ممیزی ثبت کنید (کاربر، زمان، عملیات، نشانی شبکه).

## ۶. پرسش‌هایی که برای شروع لازم است بدانیم

برای ادامه کار، پاسخ این پرسش‌ها لازم است:

1. سامانه تیکتینگ با کدام چارچوب نوشته شده؟ (Laravel / CodeIgniter / خام)
2. پایگاه‌داده آن چیست و ساختار جدول کاربران چگونه است؟ (فیلدهای کلید و کد پرسنلی)
3. آیا امکان تغییر کد سامانه PHP وجود دارد؟ (برای پیاده‌سازی SSO چه مقدار زمان دارید؟)
4. آیا سامانه تیکتینگ روی همان شبکه/دامنه سامانه اتوماسیون است؟
5. کدام سامانه «مالک» کاربران است؟ (پیشنهاد ما: این سامانه)
6. آیا تیکت‌ها باید در داشبورد سامانه اتوماسیون دیده شوند؟ (فقط خواندن یا مدیریت کامل)
7. کدام قابلیت‌ها اولویت دارند؟ (ورود واحد، دیدن تیکت‌ها در داشبورد، ایجاد تیکت از سامانه اتوماسیون، اعلان)
