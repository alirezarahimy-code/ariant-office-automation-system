# معماری پلتفرم: یک سامانه، چندین زیرسامانه

> **درس سازمانی:** سامانه تیکتینگ بدون تصویر آینده ساخته شد و چند سیستم مستقل در دل آن گنجانده شد؛ نتیجه: کاربران پراکنده، گزارش‌های پراکنده، هزینه تغییر بالا و ترس از دست‌زدن. از این پس قانون بنیادین پروژه این است: **یک پلتفرم، چندین زیرسامانه.**

---

# ۱. اصل بنیادین

سامانه اتوماسیون اداری «یک سیستم در کنار سیستم‌های دیگر» نیست؛ **پلتفرم اصلی سازمان** است. هر توانمندی موجود یا آینده، یک **زیرسامانه (ماژول)** این پلتفرم است، نه یک سیستم جدا:

- یک کاربر، یک ورود، یک منو، یک کارتابل، یک جست‌وجو، یک مبنای گزارش
- یک چارت سازمانی، یک تقویم شمسی، یک مدل مجوز و حسابرسی
- هر زیرسامانه = یک اپ جنگو در همان پروژه، همان پایگاه‌داده و همان پوسته رابط کاربری

---

# ۲. هسته پلتفرم (خدمات مشترک)

| خدمت هسته | مسئولیت |
|---|---|
| هویت و دسترسی (IAM) | کاربران، نقش‌ها، مجوزها، ورود یکپارچه، سیاست رمز، ورود دومرحله‌ای |
| تشکیلات | درخت واحدها، پست‌ها، انتصاب‌ها، جانشینی و تفویض |
| تقویم شمسی | تاریخ‌ها، تعطیلات، ساعات کاری |
| موتور گردش کار | هر جریان تأیید/پردازش در هر زیرسامانه‌ای |
| دبیرخانه و شماره‌گذاری | ثبت، شماره‌گذاری امن، مکاتبات |
| اعلان‌ها | سیستمی، ایمیل، پیامک |
| پیوست و اسناد | ذخیره‌سازی، سیاست فرمت و حجم، نسخه‌بندی |
| حسابرسی و امنیت | لاگ تغییرناپذیر، سطوح محرمانگی |
| گزارش و داشبورد | مبنای مشترک گزارش + داده زیرسامانه‌ها |
| یکپارچه‌سازی (پل) | اتصال امن به سامانه‌های موجود (PHP) تا زمان مهاجرت |

# ۳. شناسنامه زیرسامانه‌ها

| ردیف | زیرسامانه | وضعیت امروز | وضعیت هدف | ورود |
|---|---|---|---|---|
| ۱ | دبیرخانه + کارتابل | ساختنی | بومی پلتفرم | فاز ۱ |
| ۲ | گردش کار، بایگانی، جلسات، وظایف، محرمانگی، داشبورد | ساختنی | بومی پلتفرم | فاز ۲ |
| ۳ | تیکتینگ (PHP) | فعال و جدا | پل، سپس زیرسامانه بومی | پل: فاز ۱ / مهاجرت: پس از تصویب |
| ۴ | کنترل تردد (PHP) | فعال و جدا | پل، سپس زیرسامانه بومی | پل: فاز ۲ / مهاجرت: بر اساس نیاز |
| ۵ | سفارش‌گذاری و چاپ فیش (PHP) | فعال و جدا | پل، سپس زیرسامانه بومی | بر اساس نیاز |
| ۶ | انبارداری و حواله | پراکنده/کاغذی | زیرسامانه بومی | بر اساس نیاز (فاز ۳ به بعد) |
| ۷ | بازرگانی | پراکنده/کاغذی | زیرسامانه بومی | بر اساس نیاز (فاز ۳ به بعد) |
| ۸ | هر توانمندی آینده | — | فقط بومی و با قرارداد پذیرش | تصویب مدیریت |

# ۴ نردبان مهاجرت سامانه‌های PHP

| پله | اقدام | نتیجه |
|---|---|---|
| ۱ | ورود یکپارچه (SSO) + منوی واحد | یک ورود؛ سامانه موجود از منوی پلتفرم باز می‌شود |
| ۲ | نمای فقط‌خواندنی داده در کارتابل | داده سامانه موجود بدون خروج از پلتفرم دیده می‌شود |
| ۳ | بازسازی به‌صورت اپ بومی + مهاجرت داده | زیرسامانه داخل پلتفرم، با گردش کار و حسابرسی هسته |
| ۴ | بازنشستگی نسخه PHP | فقط یک سامانه می‌ماند |

> **قاعده انجماد ویژگی:** از روز رفتن پلتفرم به تولید، هیچ ویژگی جدیدی به سامانه‌های PHP اضافه نمی‌شود؛ هر درخواست جدید فقط روی پلتفرم ساخته می‌شود.

> مهاجرت هر سامانه موجود = یک فاز مستقل با تصویب، تحویل‌داری و معیار خروج خودش؛ هرگز دو مهاجرت هم‌زمان انجام نمی‌شود.

---

# ۵. قرارداد پذیرش زیرسامانه (ضد تکه‌تکه‌شدن)

1. هیچ زیرسامانه‌ای کاربر یا ورود مستقل ندارد؛ فقط IAM هسته.
2. هیچ زیرسامانه‌ای تقویم، چارت، اعلان، پیوست، حسابرسی یا گردش کار را بازسازی نمی‌کند؛ مصرف می‌کند.
3. هر جریان تأیید در هر زیرسامانه = یک تعریف روی موتور گردش کار هسته (قاعده طلایی).
4. رابط کاربری هر زیرسامانه = بخشی از پوسته پلتفرم (منو، کارتابل، پورتال)؛ نه سایت جدا.
5. جدول‌ها در همان پایگاه‌داده، با کلید خارجی به هسته (Person، OrgUnit و…).
6. سند پذیرش: یک صفحه (چرا، کدام خدمات هسته، کدام فاز، معیار خروج) + تصویب مدیریت.
7. زیرسامانه‌ای که این شرط‌ها را نپذیرد، وارد پلتفرم نمی‌شود.

# ۶. نگاشت فازها

| فاز | محتوا |
|---|---|
| فاز ۰ | هسته پلتفرم: IAM، تشکیلات، تقویم، شماره‌گذاری، حسابرسی، پشتیبان |
| فاز ۱ | زیرسامانه ۱ + پل تیکتینگ (پله‌های ۱ و ۲) → تولید محدود |
| فاز ۲ | زیرسامانه ۲ → تولید کامل |
| فاز ۳ | گسترش و مهاجرت: مهاجرت سامانه‌های موجود یکی‌یکی (پله‌های ۳ و ۴) + زیرسامانه‌های ۶ و ۷ بر اساس نیاز |
| بهره‌برداری | آموزش، پایش، به‌روزرسانی، بازنگری فصلی |

# ۷. تصویر هدف

هسته پلتفرم در مرکز؛ زیرسامانه‌ها به‌صورت ماژول در گرد آن: دبیرخانه، کارتابل، گردش کار، بایگانی، جلسات، وظایف، تیکتینگ، تردد، سفارش/فیش، انبار، بازرگانی، پورتال — همه با یک در (IAM)، یک حافظه (پایگاه‌داده هسته) و یک زبان (فارسی، شمسی، راست‌به‌چپ).

# ۸. پایان‌باز: پروژه تمام می‌شود، پلتفرم نه

- آنچه پایان فاز ۲ بسته می‌شود، **پروژه اولیه** است (دبیرخانه، کارتابل، گردش کار، بایگانی، جلسات) — نه پلتفرم.
- شناسنامه زیرسامانه‌ها (بند ۳) یک **سند زنده** است؛ سطرهای جدید در بازنگری فصلی و با تصویب مدیریت اضافه می‌شوند.
- افزودن زیرسامانه جدید = یک اپ جنگو + ثبت درمانیفست پلتفرم (منو، مجوزها، ویجت داشبورد، تعریف گردش کار)؛ نه پروژه تازه، نه کاربر تازه، نه رابط کاربری تازه.
- **هزینه نهایی** هر زیرسامانه جدید بسیار کمتر از نخستین است: آنچه یک سیستم مستقل از صفر می‌خواست (کاربر، تقویم، گردش کار، حسابرسی، پوسته UI) را زیرسامانه آماده از هسته می‌گیرد.
- نمونه: انبار و حواله = اپ `warehouse` با کلید خارجی به هسته + گردش تأیید حواله به‌صورت تعریفِ موتور گردش کار + یک آیتم منو؛ در یک فاز مستقل با تصویب و معیار خروج خودش.
- تضمین فنی باز ماندن بدون تکه‌تکه‌شدن: جدایی اپ‌ها، کلید خارجی به هسته، و قرارداد پذیرش (بند ۵).

> **پایانِ ماجرا بسته نمی‌شود؛ تنها دامنه هر فاز است که بسته می‌شود.**
