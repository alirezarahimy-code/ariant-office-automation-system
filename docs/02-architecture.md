## ۲. تصمیم‌های معماری کلیدی

### ۲-۱. تقویم شمسی
پیاده‌سازی داخلی بر پایه الگوریتم مرجع FarsiWeb (چرخه ۳۳ ساله) که با تقویم رسمی ایران در بازه ۱۳۰۴ تا ۱۴۶۷ شمسی مطابق است.

- الگوریتم ۲۸۲۰ ساله (بیرشک) **استفاده نمی‌شود**: در سال‌های ۱۴۰۳/۱۴۰۴ یک روز خطا دارد.
- صحت پیاده‌سازی با ۲۰۷ بردار مرجع تولیدشده از کتابخانه مرجع، و ۵۹٬۵۳۶ روز پیاپی سنجیده شده است.
- تاریخ‌ها در پایگاه‌داده **میلادی (UTC)** و در نمایش **شمسی** هستند.
  - دلیل: مرتب‌سازی، مقایسه، گزارش‌گیری و یکپارچه‌سازی با سامانه‌های دیگر بدون خطای تقویمی.
- برای ماژول‌هایی که تاریخ شمسی «خودِ داده» است (تاریخ نامه اداری)، تبدیل‌گر EF Core در `PersianDateValueConverter` آماده است.

### ۲-۲. دسترسی به داده
لایه کاربرد فقط `IAppDbContext` را می‌شناسد. بنابراین:
- تعویض پایگاه‌داده بدون تغییر منطق کسب‌وکار
- آزمون آسان با پایگاه‌داده درون‌حافظه‌ای

### ۲-۳. گزارش ممیزی خودکار
`AuditableEntityInterceptor` در سطح EF Core:
- مهر زمانی ایجاد/ویرایش را پر می‌کند
- هر ایجاد/ویرایش/حذف روی موجودیت‌های دامنه را در جدول `AuditLogs` ثبت می‌کند (کاربر، زمان، مقادیر پیش/پس، نشانی شبکه)
- حذف فیزیکی را به **حذف نرم** تبدیل می‌کند

نتیجه: هیچ ماژولی نمی‌تواند «از قلم بیفتد».

### ۲-۴. هویت و امنیت
- ASP.NET Core Identity با کلید `Guid` (نسخه ۷ — ترتیب زمانی برای کارایی ایندکس)
- پیام‌های خطای فارسی (`PersianIdentityErrorDescriber`)
- قفل حساب پس از ۵ تلاش ناموفق
- کوکی برای رابط وب + **نشانه JWT** برای وب‌سرویس و سامانه‌های بیرونی
- سیاست‌های مجوزدهی نام‌دار در `AppPolicies` (نه پراکندگی رشته‌ها در کد)

### ۲-۵. نبود وابستگی به CDN
فونت وزیرمتن و شیوه‌نامه در خود پروژه میزبانی می‌شوند؛ سازمان‌های با اینترنت محدود بدون مشکل کار می‌کنند.

## ۴. قراردادهای کدنویسی

| موضوع | قاعده |
| --- | --- |
| زبان کد | انگلیسی (کلاس، متد، متغیر) |
| زبان پیام‌ها و رابط | فارسی |
| نام‌گذاری موجودیت | مفرد، بدون پیشوند (`Department` نه `TblDepartments`) |
| تاریخ در پایگاه‌داده | `DateTime` میلادی، پسوند `Utc` در نام (`CreatedAtUtc`) |
| تاریخ در رابط کاربری | `PersianDate` با ارقام فارسی |
| خطاهای کسب‌وکار | `Result` / `Result<T>` (بدون استثنا برای خطای قابل پیش‌بینی) |
| جدول‌ها | جمع انگلیسی (`Departments`, `Employees`, `AuditLogs`) |
| متن‌های ثابت | در کلاس ثابت (مثل `AppRoles`)، نه پخش‌شده در کد |
| کامنت XML فایل‌های پروژه | هرگز دو خط تیره پشت‌سرهم (`--`) در کامنت نباشد؛ MSBuild نمی‌تواند فایل را بخواند و restore شکست می‌خورد |

## ۵. آماده‌سازی پایگاه‌داده

- **توسعه:** `EnsureCreated` خودکار در نخستین اجرا + داده نمونه.
- **عملیاتی:** `Database:UseMigrations = true` و ایجاد مهاجرت‌ها:

```bash
dotnet ef migrations add InitialCreate \
  --project src/Ariant.OfficeAutomation.Infrastructure \
  --startup-project src/Ariant.OfficeAutomation.Web \
  --output-dir Persistence/Migrations/SqlServer
```

سپس `Database:Provider` را روی `SqlServer` بگذارید و `dotnet ef database update` اجرا کنید.

## ۶. نگاهی به آینده: گردش کار

موتور گردش کار (فاز ۳) با این انتزاع‌ها ساخته می‌شود تا از دامنه جدا بماند:

- `WorkflowDefinition` (فرایند) → `WorkflowStep` (گام) → `WorkflowInstance` (نمونه در جریان) → `WorkflowAction` (اقدام کاربر)
- هر گام: مسئول (نقش/فرد)، شرط ورود، مهلت (بر پایه روزهای کاری با احتساب تعطیلات رسمی)
- ثبت هر اقدام در تاریخچه گردش (برای پاسخ‌گویی)

این طراحی اجازه می‌دهد بدون تغییر موتور، فرم‌های جدید (مرخصی، خرید، ماموریت) تعریف شوند.
