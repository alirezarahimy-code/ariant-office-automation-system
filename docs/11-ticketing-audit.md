# بررسی سامانه تیکتینگ (ticket v1.8-final) — دارایی‌های قابل استفاده در پلتفرم

> منبع: کلون فقط‌خواندنی در `reference/ticket` (مخزن `alirezarahimy-code/ticket`). هدف: استفاده از الگوهای آزموده‌شده به‌جای اختراع دوباره، و پاسخ به پرسش‌های ضمیمه د.

---

# ۱. تصویر کلی

- PHP سفارشی با MVC سبک (بدون فریم‌ورک): `app/{Core,Controllers,Models,Services,Views}`، `routes/web.php`، `api/inventory.php`، `cron/`، `tests/`
- پایگاه‌داده MySQL با نام `persian_ticketing`؛ منطقه زمانی Asia/Tehran؛ اعلان‌ها کاملاً درون‌سامانه‌ای
- نظم تغییرات: ده‌ها فایل `00_CHANGELOG_*` فارسی + اسناد نصب/rollback — همان «وسواس» اجرایی
- ورود: مدیر محلی + LDAP/Active Directory با نگاشت گروه AD به نقش و همگام‌سازی دوره‌ای

# ۲. زیرسیستم‌های گنجانده‌شده در تیکتینگ (شاهد زنده نیاز به پلتفرم)

| زیرسیستم | جدول‌های اصلی | سرنوشت در پلتفرم |
|---|---|---|
| هسته تیکتینگ | tickets، messages، attachments، ratings، events، sla_alerts، ticket_number_seq | پل اکنون، مهاجرت پس از تصویب |
| اموال و انبار | assets + ۹ جدول جزء و تاریخچه | زیرسامانه بومی (سطر ۶ شناسنامه) |
| کنترل تردد | traffic_destinations، traffic_visits | سطر ۴ شناسنامه |
| سفارش غذا و چاپ فیش | food_* + سرویس جدا با SQLite | سطر ۵ شناسنامه |
| رسانه CD/DVD | cd_dvd_types، cd_dvd_records | ادغام در اسناد/اموال |
| تغییر و مسئله (ITIL) | change_*، problem_records | بخشی از زیرسامانه تیکتینگ |
| پایگاه دانش | knowledge_articles | مدیریت دانش |
| سرویس کاتالوگ با فیلد پویا | service_catalog + service_catalog_fields | الهام‌بخش فرم‌ساز فاز ۳ |
| اسکن دامین | domain_scan_* | ابزار عملیات؛ بیرون از پلتفرم |

# ۳. دارایی‌های با‌وسواس → استفاده در فاز ۱

| دارایی | پیاده‌سازی در تیکتینگ | استفاده در پلتفرم |
|---|---|---|
| نقش‌ها و مجوزها | ENUM هشت‌نقشی + جدول role_permissions | تطبیق واژگان با ضمیمه ج پلتفرم |
| ساختار سازمانی | departments، org_units، org_unit_managers، handling_units | مدل OrgUnit + مدیر واحد؛ handling_units = مبنای «حوزه داده» |
| تقویم رسمی | جدول holidays | seed تقویم شمسی پلتفرم |
| امنیت ورود | login_attempts (قفل)، activity_logs، system_logs، api_rate_limits | هم‌راستا با سیاست‌های مصوب؛ انتقال الگو |
| شماره‌گذاری | جدول توالی ticket_number_seq | همان الگو برای شماره‌گذاری همزمان‌امن |
| مهلت و هشدار | ticket_sla_alerts + ola_policies | موتور مهلت پاسخ و هشدار تأخیر دبیرخانه |
| LDAP/AD | ورود دامینی، معرفی یکجا، ساخت خودکار حساب در اولین ورود، نگاشت گروه→نقش، همگام‌سازی غیرفعال‌سازی | الگوی اثبات‌شده برای «وصل کن» LDAP |
| محدوده داده | محدودسازی تیکت بر اساس حوزه رسیدگی و معاونت | پیاده‌سازی چهار سطح دسترسی ضمیمه ج |
| قرارداد SSO | توکن HMAC-SHA256 شامل role، service_group، user_id، exp؛ نشست ۸ ساعته؛ بدون اعتبارنامه در URL | قرارداد رسمی پل پلتفرم (به‌روزرسانی ضمیمه د) |

# ۴. پاسخ به هفت پرسش باز ضمیمه د (از دل کد)

| پرسش | پاسخ یافته |
|---|---|
| چارچوب تیکتینگ؟ | MVC سفارشی PHP (لاراول نیست) |
| امکان افزودن ماژول؟ | بله؛ سابقه عملی: سرویس غذا، client-agent |
| مالک کاربران؟ | امروز: تیکتینگ + AD؛ هدف: پلتفرم با IntegrationUserMap |
| فقط‌خواندنی کافی است؟ | بله؛ مطابق قرارداد موجود |
| پایگاه‌داده؟ | MySQL `persian_ticketing`؛ دسترسی فقط‌خواندنی نیازمند تأیید شما |
| حجم تیکت‌ها؟ | نیازمند کوئری روی سرور زنده (دسترسی ندارم) |
| الزام امنیتی ارتباط؟ | HMAC-SHA256 با کلید مشترک + گزینه ENFORCE_HTTPS + rate limit؛ چرخش کلیدها پیش از اتصال |

# ۵. بدهی‌های دیده‌شده (برنامه مهاجرت)

- تعریف نقش در دو جا (ENUM در users و VARCHAR در role_permissions) → در پلتفرم: تک‌منبع
- SQLite جدا برای سرویس غذا → یکپارچگی در پلتفرم
- بدون migration؛ فقط schema.sql و اسکریپت‌های rebuild/rollback → پلتفرم: مایگریشن جنگو
- چرخش اعتبارنامه‌های .env تولیدی پیش از هر اتصال

# ۶. اقدام فاز ۱ با این دارایی‌ها
