# سند تصمیم فنی: انتخاب پشته فناوری سامانه

> تاریخ: ۱۴۰۵/۰۷/۲۰ — مبنا: **آزمون عملی در محیط اجرای دستیار**، نه مقایسه نظری.

## معیار تصمیم

خواسته صریح کارفرما: پشته‌ای که دستیار بتواند **بنویسد، بسازد، اجرا کند و تست کند** و در نهایت کارفرما عیب‌یابی و گسترش دهد. پس معیار اصلی، «توان خودآزمایی» است.

### جزئیات دو یافته مهم

**الف) Prisma رد شد — دو دلیل مستقل:**
1. برچسب `latest` آن به یک نسخه **RC آزمایشی** (۸.۰.۰-rc.22) اشاره می‌کند که دستورهای اصلی (`generate`، `db push`) را حذف کرده است؛ یعنی `npm i prisma` در آینده پروژه را می‌شکند.
2. حتی با تثبیت نسخه پایدار ۷.۱۰.۰، موتور آن از `binaries.prisma.sh` دانلود می‌شود که در این محیط بسته است ⇒ دستیار نمی‌تواند مهاجرت پایگاه‌داده را بسازد یا آزمون کند.

**ب) کتابخانه‌های تاریخ شمسی جاواسکریپت قابل اعتماد نیستند:**
- `dayjs + jalaliday`: **۱۵ خطا در ۵۰۰ تاریخ تصادفی** (یک روز عقب‌تر) — نمونه تأییدشده دستی: `2020-02-15` باید `1398/11/26` باشد ولی این کتابخانه `1398/11/27` می‌دهد.
- خطاها در سال‌های ۱۳۱۴، ۱۳۴۶، ۱۳۵۰، ۱۳۸۶، ۱۳۹۸، ۱۴۱۰، ۱۴۱۸، ۱۴۲۶، ۱۴۳۴، ۱۴۳۸ و ۱۴۶۲ هستند؛ یعنی همان خانواده الگوریتم حسابی (۲۸۲۰ ساله) که پیش‌تر رد شد.
- **ICU مرورگر/Node: صفر خطا در ۵۰۰ تاریخ.**
- تصمیم: موتور تقویم **اختصاصی پورت‌شده از کد .NET** (الگوریتم ۳۳ ساله FarsiWeb، آزمون‌شده با ۲۰۷ بردار و ۶۳٬۸۳۹ روز پیاپی) به TypeScript منتقل می‌شود و ICU فقط به‌عنوان شاهد دوم در آزمون‌ها به کار می‌رود.

## ۲) پشته پیشنهادی

| لایه | انتخاب | چرا |
|---|---|---|
| زبان | **TypeScript (strict)** | کامپایل نوع‌دار در همین محیط، خطاها پیش از اجرا گرفته می‌شود |
| بک‌اند | **NestJS 12** | ماژولار و لایه‌ای؛ مفاهیمش (Module/Controller/Service/DTO/Guard) برای ذهن یک توسعه‌دهنده .NET آشناست |
| ORM | **Drizzle ORM + drizzle-kit** | سبک، نوع‌دار، مهاجرت SQL خوانا، بدون دانلود باینری |
| پایگاه‌داده | **PostgreSQL** (تولید) / **SQLite** (توسعه و آزمون) | SQLite کاملاً در این محیط آزمون‌پذیر است |
| رابط کاربری | **React 19 + Vite + Ant Design 6** | کامپوننت‌های اداری آماده، پشتیبانی رسمی RTL و زبان fa_IR، فونت وزیرمتن محلی |
| آزمون | **Vitest** (+ `supertest` برای API) | اجرای سریع در همین محیط |
| اتصال به تیکتینگ PHP | HTTP + JWT با کلید مشترک | سامانه PHP دست‌نخورده می‌ماند؛ فقط یک ماژول «پل» در دو طرف اضافه می‌شود |

## ۳) آنچه از کار .NET منتقل می‌شود (هدر نمی‌رود)

- **۲۰۷ بردار آزمون تقویم شمسی** به‌عنوان داده طلایی آزمون انتقال می‌یابد.
- الگوریتم تأییدشده و مستندات فارسی (`docs/01` تا `docs/04`).
- قواعد معماری: ممیزی خودکار، حذف نرم، شناسه‌های GUID، زمان UTC + نمایش شمسی.
- سامانه تیکتینگ و طرح پل SSO (`docs/04-ticketing-integration.md`) بدون تغییر معتبر می‌ماند.

## ۴) ریسک‌های شناخته‌شده پشته TypeScript (پیش از تصمیم بدانید)

1. پایگاه‌داده PostgreSQL/MySQL در این محیط **اجرا نمی‌شود**؛ آزمون‌های پایگاه‌داده روی SQLite انجام می‌شود. تفاوت لهجه SQL را باید یک‌بار روی سرور خودتان بررسی کنیم (مهاجرت‌ها SQL استاندارد تولید می‌کنند).
2. پکیج‌هایی که فایل باینری را از دامنه‌ای جز npm می‌گیرند (مانند Prisma) در این محیط نصب نمی‌شوند؛ انتخاب ORM بر همین مبنا انجام شد.
3. TypeScript نسخه جدید چند سختگیری افزوده است (`rootDir`، `types: ["node"]`، اعلام `*.css`) — راه‌حل‌ها آزمون و ثبت شد.
4. برای اجرا روی سرور ویندوزی: Node 22 به‌همراه NSSM/PM2 یا Docker؛ ویندوز سرویس + IIS به‌عنوان پروکسی معکوس (ARR).

## ۵) تصمیم

پشته **Node.js + TypeScript (NestJS + Drizzle + React/AntD)** توصیه می‌شود، چون تنها گزینه‌ای است که در آن حلقه «نوشتن ← ساخت ← اجرا ← تست ← پیش‌نمایش زنده» **کامل در اختیار دستیار** است و کارفرما می‌تواند روی کد و مهاجرت‌های SQL خوانا، عیب‌یابی و گسترش دهد.

انتخاب نهایی با کارفرماست؛ در هر دو حالت، مستندات و بردارهای آزمون موجود سرمایه مشترک پروژه هستند.

## ۶) ارزیابی پایانی — پس از آزمون پایتون (دور دوم)

**یک سوءتفاهم که باید صریح رفع شود:** «TypeScript» که پیشنهاد شد، ربطی به «.NET» ندارد؛ TypeScript زبان برنامه‌نویسی خانواده جاواسکریپت روی موتور Node.js است. .NET (سی‌شارپ) اصلاً توصیه من نبود و نیست، چون SDK آن در محیط دستیار نصب‌نشدنی است و هر تغییر فقط با CI گیت‌هاب (~۲ دقیقه هر دور) آزمون می‌شود.

### نتیجه آزمون واقعی پایتون + جنگو

| مورد | نتیجه |
|---|---|
| نصب Django 5.2 | ✓ در چند ثانیه |
| ساخت پروژه، مدل، مهاجرت پایگاه‌داده | ✓ `makemigrations` + `migrate` بدون خطا |
| اجرای آزمون | ✓ دو آزمون پایگاه‌داده‌ای با متن فارسی سبز |
| **پنل مدیریت** | ✓ **فارسی و راست‌به‌چپ به‌صورت خودکار** (`dir="rtl"`, `lang="fa"`)، عنوان «ورود \| مدیریت وب‌گاه» |
| درج و نمایش داده در پنل | ✓ سه واحد سازمانی با عنوان فارسی در فهرست پنل مدیریت دیده شد |
| آماده بودن برای رابط React | ✓ DRF 3.18.3 نصب شد |

### رتبه‌بندی نهایی بر پایه شواهد

| رتبه | گزینه | دلیل اصلی | مناسب برای |
|---|---|---|---|
| **۱** | **پایتون + جنگو + DRF** | تنها گزینه با **پنل مدیریت فارسی آماده**؛ حذف هفته‌ها کار تکراری؛ کل چرخه ساخت/اجرا/تست در محیط دستیار؛ بسته‌های آماده شمسی، ممیزی، درخت سازمانی و تولید اسناد | هسته سامانه اتوماسیون اداری، دبیرخانه، منابع انسانی |
| ۲ | TypeScript (NestJS + React/AntD) | مدرن‌ترین رابط کاربری؛ نوع‌دان قوی؛ کل چرخه در محیط دستیار | پورتال کاربری زیبا و ماژول‌های تعاملی (به‌عنوان لایه روی DRF) |
| ۳ | PHP 8.4 | فقط منطق پایه قابل آزمون است (بدون PDO/curl/mbstring) | **پل سامانه تیکتینگ فعلی** — نه سامانه جدید |
| ۴ | .NET (سی‌شارپ) | SDK در محیط دستیار نصب نمی‌شود؛ چرخه آزمون کند | فقط اگر تیم سازمان اجبار داشته باشد |

**توصیه:** هسته با **پایتون/جنگو** (سریع، آزمون‌پذیر، پنل فارسی آماده) و در صورت نیاز، پورتال کاربری با **React/AntD** روی API جنگو. سامانه تیکتینگ PHP دست‌نخورده می‌ماند و پل، HTTP + JWT خواهد بود.
