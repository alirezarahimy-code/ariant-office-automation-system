> **هشدار نسخه:** این مستند مربوط به پنل مستقل C# قدیمی است، نه منبع سفارش داخلی نسخهٔ فعلی. برای ماژول جاری از [راهنمای عملیاتی 1.38](../FOOD-ORDERS-1.38-OPERATIONS-fa.md) استفاده کنید؛ سرویس C# را برای سفارش داخلی اجرا نکنید. Access سفارش غذا در مسیر جاری خوانده نمی‌شود و Access تردد TENTER جدا باقی است.

# سامانه مستقل فیش غذا

این نسخه پنل و موتور C# مستقل دارد و ورود SSO را از سامانه اصلی می‌پذیرد؛ اما خود سرویس C# به MySQL سامانه اصلی وصل نیست. پنل فقط برای ادمین اصلی و مدیر پشتیبانی قابل استفاده است.

سرویس در حالت `integrated` اجرا می‌شود. لینک «چاپ فیش غذا» در سامانه اصلی فقط برای ادمین اصلی و مدیر پشتیبانی نمایش داده می‌شود؛ کاربران عادی، سوپروایزر و مدیر واحد هم از مسیر مستقیم مجوز ورود ندارند. ادمین اصلی همهٔ فرم‌ها را می‌بیند، اما مدیر پشتیبانی فقط داشبورد، پایش، سفارش‌های غذا، کارکنان و گزارش‌ها را می‌بیند. سرویس در حالت نصب معمول کلید `app.key` را از `config.php` پوشهٔ والد می‌خواند؛ اگر پنل جداگانه اجرا می‌شود، مقدار `ssoKey` باید با `food_ticket.sso_key` سامانه اصلی یکسان باشد.

## رفتار اصلی

1. سرویس، جدول `SOURCE_TABLE` را آنلاین و دوره‌ای می‌خواند.
2. کد پرسنلی/کارت از SOURCE_TABLE کارمند را در فهرست کارکنان پیدا می‌کند؛ سفارش غذا با کد ملی همان کارمند تطبیق داده می‌شود.
3. رکورد پردازش‌شده در SQLite محلی و جدول `tblLiveMonitoring` در فایل Access سفارش ثبت می‌شود؛ این سرویس مانیتورینگ را به MySQL نمی‌نویسد.
4. فیش از طریق چاپگر شبکه‌ای TCP/RAW، معمولاً پورت `9100`، چاپ می‌شود.
5. بعد از ثبت پایدار نتیجه و پایان پردازش، رکورد متناظر از `SOURCE_TABLE` حذف می‌شود.
6. نتیجه چاپ و خطا برای گزارش و چاپ مجدد در مانیتورینگ باقی می‌ماند.
7. سرویس بدون دکمهٔ پردازش دستی، جدول را با فاصلهٔ تنظیم‌شده پایش می‌کند.
8. در تنظیمات، زیرفرم‌ها به‌صورت تب نمایش داده می‌شوند و فقط زیرفرم انتخاب‌شده در صفحه می‌ماند.

## قواعد موتور پایش

- `L_UID` با `tblEmployees` تطبیق داده می‌شود و کاربر ناشناس/غیرفعال جدا ثبت می‌شود.
- سفارش فقط وقتی معتبر است که کد ملی و تاریخ غذا با تاریخ تردد یکی باشد. کد پرسنلی از جدول سفارش لازم نیست.
- تردد تکراری همان هویت در همان روز دوباره چاپ نمی‌شود.
- کارت مهمان از `C_Card` با تنظیمات `GuestCardUIDs`، `MaxGuestTicketsPerDay` و `GuestFoodType` کنترل می‌شود.
- نتیجه قبل از چاپ در مانیتورینگ ثبت می‌شود؛ در خطای چاپ، رکورد `SOURCE_TABLE` حذف نمی‌شود و از گزینهٔ چاپ مجدد قابل تلاش است.
- نام و لوگوی پنل از `brandName` و `brandLogo` در `food_ticket_config.json` خوانده می‌شود و از بخش تنظیمات پنل نیز قابل تغییر است.
- حذف `SOURCE_TABLE` فقط پس از تصمیم نهایی یا چاپ موفق انجام می‌شود و با UID/تاریخ/ساعت تلاش می‌شود.

## اجرای واقعی روی Windows

1. کل پوشهٔ `food-ticket-web` را روی همان Windows Server یا کامپیوتری قرار دهید که به فایل‌های Access و چاپگر شبکه دسترسی دارد.
2. `install_prerequisites.bat` را اجرا کنید تا .NET 8 SDK بررسی و بسته‌ها Restore شوند؛ Microsoft Access Database Engine نیز باید با معماری پردازش .NET هماهنگ باشد.
3. فایل `food_ticket_config.json` را از روی نمونه بسازید، برای دست‌کم یک مدیر رمز بگذارید و مسیرها، نام ستون‌ها، کلید SSO، چاپگر و مسیر گزارش را تکمیل کنید.
4. `start_food_ticket.bat` سرویس را به‌طور پیش‌فرض فقط روی همین رایانه (`http://127.0.0.1:8080`) اجرا می‌کند. برای دسترسی شبکه‌ای، تنظیم آگاهانهٔ `FOOD_TICKET_URL` و HTTPS روی شبکهٔ مدیریتی لازم است؛ سرویس به‌تنهایی TLS ندارد.
5. پنجرهٔ CMD را تا پایان استفاده باز نگه دارید؛ برای هر فیش لازم نیست سرویس را دوباره اجرا کنید.
6. انتخاب‌گر فایل/پوشه فقط وقتی کار می‌کند که سرویس در همان Windows و به‌صورت تعاملی اجرا شود.

فایل `index.html` که مستقیماً باز می‌شود، برای پیش‌نمایش مستقل و بدون اتصال واقعی هم کار می‌کند. اتصال آنلاین Access/ODBC از طریق سرویس .NET انجام می‌شود.

در صفحهٔ چاپگر، گزینهٔ «دریافت چاپگرهای نصب‌شده» فهرست چاپگرهای Windows را می‌خواند. چون چاپگر شبکه روی سرور نصب می‌شود، روش پیشنهادی `Windows Spooler` است و نیازی به واردکردن IP در خود برنامه ندارد.

فرم کارکنان از `tblEmployees` فایل سفارش وارد می‌شود و تغییرات کارکنان و کارت‌های مهمان در SQLite محلی سرویس نگه‌داری می‌شوند؛ این تغییرات به MySQL یا Access بازنویسی نمی‌شوند. مسیرهای CRUD پنل از طریق API سرویس اعمال می‌شوند. پنل با عرض واکنش‌گرا باز می‌شود و تاریخ‌های ورودی/نمایشی شمسی هستند.

فرم سفارش غذا و فرم پایش خواندنی هستند؛ انتخاب تاریخ «امروز» در سفارش‌ها فقط فیلتر را تغییر می‌دهد و هیچ رکوردی از این دو فرم ویرایش نمی‌شود. پایش دستی حذف شده و سرویس پس‌زمینه مسئول دریافت و پردازش آنی است.

پنل پیش‌نمایش و طراحی فیش دارد، اما موتور RAW فعلی فقط قالب متنی ثابت را چاپ می‌کند؛ مختصات و فیلدهای بوم طراحی هنوز به خروجی واقعی چاپگر اعمال نمی‌شوند.

گزارش‌ها با دکمهٔ خروجی Excel به‌صورت فایل واقعی `.xlsx` در مسیر تعیین‌شده در تنظیمات سیستم ساخته می‌شوند و برای این بخش وابستگی Excel جداگانه‌ای لازم نیست.

اگر فقط `index.html` مستقیم باز شود و سرویس Windows اجرا نباشد، همان دکمه یک فایل Excel قابل‌گشایش با پسوند `.xls` برای دانلود می‌سازد؛ ذخیره مستقیم در مسیر سرور فقط از طریق سرویس Windows انجام می‌شود.

تاریخ‌های متنی کوتاه مانند `20260506` و ساعت‌های `102036` در سرویس به‌ترتیب به `2026-05-06` و `10:20:36` تبدیل می‌شوند. تاریخ نمایشی پنل شمسی است.

## ستون‌های سفارش

سفارش غذا از جدول داخلی `food_orders` خوانده می‌شود (ثبت‌شده در برنامه غذایی). منبع سفارش Access (food_fish / orders_path / orders_table) حذف شده است؛ Access فقط برای تردد TENTER استفاده می‌شود.
فقط یکی از دو موتور را اجرا کنید: PHP `cron/food_ticket_worker.php --loop` یا سرویس C#؛ اجرای هم‌زمان می‌تواند یک تردد را دوباره پردازش کند.
